三维部分可观测多无人机协同捕获：下一阶段实验补充计划（V10）
日期：2026-08-21
仓库：https://github.com/Liangxianguang/uav_capture

======================================================================
0. 这份计划要解决什么问题
======================================================================

当前已经能够严谨说明的结论：
    1) V4 已在三维、静态混合障碍、合成部分可观测、运动学环境中完成正式
       3-seed locked-test。retained policy + CBF 的 S3 Cooperative Safe Capture
       为 75.3% +/- 6.5%。
    2) raw policy 的碰撞率很高，主要安全收益来自 CBF；论文和报告必须始终
       将 raw actor 与 policy + CBF 分开。
    3) 测量时延与突发遮挡压力测试已完成，现有 belief 特征没有给出稳定增益。
       这是一条已记录的失败边界，不应重复堆叠同类感知模块。
    4) V5 的三 seed development 未全部通过，唯一预注册的 P3-A 墙体覆盖恢复
       也已被拒绝。因此 V5 locked block 647201 永不打开，不再继续调参。

目前最需要补的缺口：
    运动学仿真中，CBF 输出的“下一时刻速度”被立即、精确地执行；真实无人机
    会有控制保持、执行延迟、有限加速度和执行误差。尚不知道现有捕获策略在
    这些执行约束下是否仍能安全捕获，也不知道运动学 CBF 是否因执行失配而失效。

本计划的唯一主目标（E1）：
    在不改动捕获任务、观测任务和 V4 学习策略的前提下，建立一个可复现的
    “受限动作执行”三维追逃基准，量化冻结 V4 策略在执行延迟、加速度受限和
    执行噪声下的性能退化，并比较 raw actor、原运动学 CBF 与执行感知 CBF。

两句研究表述：
    多无人机协同捕获在理想速度控制下可行，但动作不能被瞬时执行时，安全层的
    运动学假设可能失效，导致碰撞或捕获率下降。
    我们用一个参数可追溯的动作执行模型和保守的执行感知 CBF，测量并缓解这种
    sim-to-sim 执行失配，而不将其误称为实飞验证。

2. E1 的方法定义（先写进配置，再运行任何 development 评估）
======================================================================

2.1 冻结的策略来源

[ ] 创建 E1_SOURCE_MANIFEST.json，登记三个 V4 正式 retained-policy checkpoint：
    checkpoint 路径、SHA-256、产生它的 git commit、训练 YAML、训练 seed、CBF
    源码 hash 和软件环境。三个独立 checkpoint 才是统计重复单位。
[ ] 若本地没有上述 checkpoint，只允许按冻结的 V4 YAML 重新生成同一来源的
    checkpoint；不得因 E1 结果重新训练、挑选或微调策略。
[ ] E1 的 nominal (E0) 回放仅用于验证执行包装器的恒等性；其新 episode 不替代
    V4 的历史 locked-test 数字。

2.2 受限动作执行链

[ ] 新建独立模块（建议 src/encirclement3d/execution_dynamics.py），不要直接在
    用户修改的 pursuit_env.py 中叠加 E1 逻辑。默认 disabled 时环境行为必须与
    当前主线一致。
[ ] 每个控制步明确记录如下链路：
        policy velocity command
          -> raw / kinematic-CBF / execution-aware-CBF command
          -> FIFO control-delay queue
          -> acceleration and speed limiter
          -> bounded execution noise
          -> executed defender velocity -> position update
[ ] 执行状态至少包括：上一实际速度、待执行命令队列、控制命令年龄、随机噪声
    状态和各类饱和标志；reset 必须清空全部状态。
[ ] 固定离散模型（变量与实际数值均写入 YAML 和 episode JSON）：
        c_t       = safety-filtered velocity command
        q_t       = c_(t-d)                 (d 为整数控制步延迟)
        v_pre     = clip_delta(q_t, v_(t-1), a_exec * dt)
        v_exec    = clip_speed(v_pre + epsilon_t, v_max_exec)
        p_(t+1)   = p_t + v_exec * dt
    epsilon_t 的分布、独立性、随机种子和限幅必须固定；不要声称其来自真实飞控标定。
[ ] 只使用当前任务已知的状态构造 CBF；执行感知 CBF 不得读取未来目标轨迹、真实
    全局地图以外的新信息，或绕过现有局部观测/通信合同。

2.3 三个必须并列的执行方式

[ ] Raw：policy command 直接进入受限执行链。
[ ] K-CBF：现有离散时间运动学 CBF 输出进入同一受限执行链。它是“忽略执行失配”
    的安全层基线。
[ ] E-CBF：执行感知 CBF 输出进入同一受限执行链。其延迟、速度、加速度、噪声界
    必须仅由 2.2 的预注册模型推导；不能看 development 成功率后修改 margin。
[ ] 三种方式必须在每个 policy checkpoint、episode seed、静态地图、初始状态、
    target profile 和执行噪声种子上完全配对。

在 E1 的所有源码、YAML、协议和测试提交后，创建
E1_EXECUTION_DYNAMICS_PREREGISTRATION.md/.json。下列 profile 必须在运行任何
development 政策评估前冻结；具体 m/s、m/s^2 和 dt 均从 effective YAML 导出。

| ID | control delay d | a_exec / a_nominal | noise sigma / v_max | 用途 |
|----|-----------------|--------------------|---------------------|------|
| E0 | 0 step          | 1.00               | 0.00                | 恒等性/名义参考 |
| E1 | 0 step          | 0.75               | 0.00                | 单因素制动不足 |
| E2 | 0 step          | 0.50               | 0.00                | 强制动不足 |
| E3 | 1 step          | 1.00               | 0.00                | 单步命令保持 |
| E4 | 2 steps         | 1.00               | 0.00                | 双步命令保持 |
| E5 | 0 step          | 1.00               | 0.05                | 有界执行噪声 |
| E6 | 1 step          | 0.75               | 0.05                | 预注册的组合主压力 |

[ ] E6 是本轮唯一的“主压力条件”；E1-E5 是机制诊断条件。七个 profile 都必须进入
    正式 locked-test，不能根据 development 结果删除困难条件或新加条件。
[ ] 噪声只加在执行端，不能泄漏给策略观测；每个 episode 的 noise seed 写入 CSV/
    JSON，raw/K-CBF/E-CBF 共享该 seed。
[ ] 使用全新的 E1 episode seed block：
    - smoke block：681001（仅链路检查，不产生结论）；
    - development block：681101（调试和代码正确性检查）；
    - locked block：681201（首次正式运行前不得读取、重放、渲染或用于任何选择）。
[ ] 固定 S1/S2 场景和随机 S3 地图均由各 block 的 case seed 生成。每个 case 的
    static-scene SHA、initial-state SHA、target-profile SHA、noise-seed 必须保存，
    并由评估器自动断言三种执行方式完全配对。

4. P0：环境增量实现与单元契约（不做正式评估）
======================================================================

目标：证明新增执行模型没有悄悄改变旧环境，且其数学行为可逐步复现。

[ ] P0.1 新建 execution dynamics dataclass、YAML schema、effective-config 导出和
    episode-level audit 字段；默认 execution_enabled=false。
[ ] P0.2 在 E0 下，对固定 reset、固定动作序列进行逐步回放。新增包装器与原环境

    （浮点量用明确的 1e-12 容差）；否则停止，不进入 E1-E6。
[ ] P0.3 为 FIFO 延迟、加速度限幅、速度限幅、噪声可复现性、reset、不同 pursuer
    独立队列和异常 NaN/Inf 输入分别写最小单元测试。
[ ] P0.4 单独测试 K-CBF 与 E-CBF 均满足速度/加速度可执行域；所有 QP/fallback
    必须记录 status，禁止静默回退或吞掉不可行状态。
[ ] P0.5 构造一个手工可验证的“靠近墙体后急转”轨迹：证明执行延迟确实使 K-CBF
    的实际轨迹不同；同时检查 E-CBF 的保守边界符合预注册的误差界。该轨迹只是
    单元测试，不是论文成功示例。
[ ] P0.6 smoke：每 profile 跑 10 个 rule-expert + E-CBF episode 与 10 个冻结 policy
    episode，检查文件、指标和配对哈希；smoke 数据绝不进聚合结果。

通过条件：所有定向测试通过；E0 恒等性通过；没有 NaN/Inf、隐藏 reset 状态或
未记录的 CBF fallback。失败时只修实现，不依据 policy 成功率调参数。
